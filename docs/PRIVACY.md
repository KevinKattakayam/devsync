# Privacy and data lifecycle

This is a source-based implementation inventory, not a public-service privacy notice, legal opinion or GDPR/DPDP compliance certification. The deployment operator must identify the controller/data fiduciary, processors, contact, purposes, lawful basis, locations and applicable obligations before processing real user data. No production vendor agreements, deletion exercise or legal review were verified here. Sources are linked below; measured security results are in [FINAL_REPORT.md](FINAL_REPORT.md).

## Retention: behavior is not a policy

| Store                                                                 | Current behavior                                                                       | Gap for the operator                                                                                                |
| --------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Workspace content, history/backups, activities and accepted decisions | Retained without a general age-based purge. Archive hides content; it is not deletion. | Define purpose-based periods, legal holds and derivative cleanup. Do not delete recovery records casually.          |
| Invitations                                                           | Seven-day validity; acceptance/revocation/expiry controls use.                         | Invalid invitations can remain stored; define cleanup.                                                              |
| Digest                                                                | Seven-day eligible-event window; personal preference/checkpoint persists.              | The view window is not a seven-day deletion policy.                                                                 |
| Create-idempotency receipts                                           | 24-hour expiry with bounded opportunistic cleanup for the acting authority.            | Inactive-authority expired records need scheduled reviewed cleanup; TTL does not prove physical deletion.           |
| AI counters / concurrency                                             | Counters expire after90 days of inactivity; leases expire after120 seconds.            | These are admission mechanics, not a financial/legal retention schedule. Protect shared Redis backups.              |
| BullMQ work                                                           | Default queues keep up to500 completed and1000 failed jobs; DLQ can retain payloads.   | Count caps are not retention days or guaranteed erasure across all queues/providers. Review job data and incidents. |
| Logs, browser copies and backups                                      | No general application-enforced retention/purge schedule.                              | Select access controls/expiry, document restores and reconcile deletions/revocations after restoring old data.      |

## Access, correction, export and deletion

There is no implemented general self-service account export, workspace export bundle, account-deletion workflow or cross-provider erasure service. A database backup is not a subject-access export and can expose other tenants. The local profile API has limited correction fields; changes to identity email/provider records require Clerk coordination. SCIM deactivation/membership operations are not complete account erasure.

An owner can request workspace deletion through the existing policy/transaction path. Declared cascades and FK restrictions govern database effects; retained CRDT backups and related records can restrict deletion. This does not erase Clerk identities, logs, Redis jobs, vendor copies, browser downloads or old backups. Do not promise a successful end-to-end erasure merely from an HTTP response or archive operation. Sources: [workspace controller](../backend/src/controllers/workspace.controller.ts), [auth routes](../backend/src/routes/auth.routes.ts), [schema](../backend/prisma/schema.prisma).

Until an actual rights workflow is built, the operator must provide a verified private request channel, authenticate the requester and scope, review lawful retention/holds with counsel, identify all stores/providers, and prepare any authorized export in isolated protected tooling. Recheck tenant boundaries before delivery; do not send full database dumps. A reviewed deletion plan must cover derivatives, queues, provider records and backup/restore handling, with auditable outcomes. These are required operating procedures, not a supplied deletion script or promise that a request has been fulfilled.

## AI and external processing

When keys are configured, interactive requests can send prompts, selections and retrieved workspace context to Groq/OpenAI. Query/resource embeddings use OpenAI where configured. Background indexing and task/PR summaries can also disclose content after their service/tenant checks; enabling provider keys is not a per-user consent workflow. Quotas do not provide legal consent or a strict monetary ceiling.

Document/snippet/task text is treated as untrusted input. Sources are retrieved candidates, not guaranteed claim support. Generated output is labeled in the relevant UI; neither labels nor redaction prove confidentiality. The code does not implement model training, but it cannot establish a vendor's no-training, retention, residency or deletion commitments. Operators must review model availability, vendor terms/DPAs, transfers, purpose/notice and provider-side spending caps. No live provider evaluation or contractual assurance is part of the test record. See [AI_COST_SAFETY.md](AI_COST_SAFETY.md), [AI provider policy](../backend/src/services/ai-provider.ts) and [evaluation scaffold](../backend/testing/ai-eval/README.md).

Clerk, GitHub, Stripe, optional telemetry/reporting/Cloudinary and hosting/storage services need a deployment-specific subprocessor/vendor inventory. No fixed data region or exhaustive provider retention claim is supplied by repository configuration.

## GDPR and DPDP basics requiring legal review

GDPR rights include transparency, access, rectification, qualified erasure, restriction, objection and portability; operators need procedures to facilitate them. The available rights and exceptions depend on the processing. DevSync's authorization and partial profile API do not implement that full rights process. Counsel must assess territorial scope, controller/processor roles, lawful bases, notices, contracts, transfers, security, breach handling and retention. [European Data Protection Board: data-subject rights](https://www.edpb.europa.eu/topics/key-gdpr-concepts/data-subject-rights_en).

India's DPDP Act addresses grounds for processing, notice/consent, fiduciary safeguards and rights including access information, correction/erasure, grievance redressal and nomination. Applicability, children, exemptions, transfers and operator responsibilities need review; this repo does not implement consent-manager, guardian verification or grievance automation. [Official DPDP Act](https://www.meity.gov.in/static/uploads/2024/02/Digital-Personal-Data-Protection-Act-2023-1.pdf).

The notified2025 Rules have phased commencement: some on publication, Rule4 after one year, and the specified remaining group after eighteen months. Do not label every provision currently effective or substitute a generic GDPR workflow for DPDP. Counsel must verify the Act's separate commencement notifications, applicable dates and any amendments for the actual launch. [Official2025 Rules, rule1](https://www.meity.gov.in/static/uploads/2025/11/53450e6e5dc0bfa85ebd78686cadad39.pdf). No legal-compliance claim, certification, legal opinion or completed legal review is made.
