## Fixture-only preflight endpoint

The test executable mounts `GET /__fixture/load-preflight` after `validateFixtureConfiguration` verifies test mode, the disposable database naming rule and the per-run capability format. A matching `x-e2e-run-secret` header returns only a versioned marker and a random run ID stable for that server process; missing or incorrect capabilities return 403. Responses are no-store. The endpoint is not registered by the production application. Possession of the capability and a marker are fixture checks, not proof against a malicious local server or proof of database isolation beyond the existing configuration safeguards. Never log or include the capability in evidence.

Focused endpoint tests passed 2/2 using a permitted local subprocess; the first sandboxed attempt failed before assertions with `listen EPERM`. Focused ESLint, Prettier and backend typecheck passed. The focused Jest command used `--coverage=false` and is not a full coverage gate. The existing k6 workload has not yet been connected to this endpoint; no load was executed. ## k6 fixture gate

`tools/quality/load.js` requires `K6_BASE_URL` in the exact form `http://127.0.0.1:<port>/api`, the private 64-hex `K6_FIXTURE_CAPABILITY`, a fixture access token, and bounded workspace/document IDs. Setup calls the fixture-only preflight with redirects disabled and rejects any non-200, malformed or unexpected versioned marker/run ID before VUs start. Each iteration rechecks the same run ID before its four reads and aborts the test on failure; workload redirects are also disabled. This adds a preflight request to each iteration and contributes to k6 HTTP totals. The capability and token must be supplied privately and never recorded in logs or results.

The fixture server enforces its existing test-mode/database-name configuration and capability check; the marker is not cryptographic attestation against a malicious local listener and does not prove physical isolation or a synthetic identity on its own. Use only an explicitly prepared disposable fixture and its fixture-issued token. The endpoint accepts the capability in a header, so do not use HTTP debugging or capture request headers. Existing endpoint tests exercise invalid capabilities; local Node tests exercise response validation and workload sequencing with mocked k6 APIs. Actual k6 runtime and fixture execution remain pending because k6 is unavailable here. No latency, throughput, provider or load result is claimed.
