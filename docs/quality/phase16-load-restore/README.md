## k6 fixture gate

## Isolated k6 fixture orchestrator and child launcher

`backend/testing/fixture-lifecycle.ts` now owns the PostgreSQL/Redis provisioning, migration, seed and non-bypass runtime-role setup shared by the existing browser runner and load runner. The browser runner still uses its original `devsync_e2e_browser` database, port 5501, environment switches, frontend setup and Playwright invocation. The load runner uses a fresh random `devsync_e2e_load_<suffix>` database and loopback port; each invocation receives separately created PostgreSQL and Redis containers. Migrations/seeding use the disposable container's admin connection, then the fixture server receives only the `browser_runtime` `NOBYPASSRLS` connection. Its environment is an explicit allowlist and omits `E2E_ADMIN_DATABASE_URL`, seed credentials, inherited cloud/proxy settings and arbitrary `K6_*` values.

The runner is opt-in and rejects remote Docker endpoints/contexts, host overrides, container reuse and disabled Ryuk cleanup. It refuses to start containers when k6 is not present on `PATH`. It binds the fixture server to an allocated `127.0.0.1` port, checks health, validates the exact versioned fixture preflight with the fresh run capability, logs in only as `sample-owner@devsync.invalid`, obtains a short-lived fixture access token via the protected session token route, and verifies that token resolves to that seeded identity and workspace membership. Only then does it call `launchFixtureSmoke`; the k6 child receives capability/token through the fixed environment allowlist, never argv or logs. k6 repeats its preflight before VUs and each iteration.

The smoke remains bounded to two VUs for 15 seconds. The launcher reads only an allowlist of finite numeric latency/count/rate fields from the fixed k6 summary, discards the raw summary and temporary directory, and excludes request headers, token values, response bodies and arbitrary metric fields. On a successful run, the CLI writes a mode-0600, gitignored JSON file under `docs/quality/phase16-load-restore/results/`; generated result JSON must be reviewed before any separate evidence is retained. Aggregate `http_req_duration` and `http_reqs` include fixture preflight requests; the four named endpoint trends describe application reads. These are provisional fixture measurements, not production SLOs.

Run from a normal local Linux terminal with backend dependencies installed, Docker access to the local Unix socket, k6 on `PATH`, and the repository on a writable filesystem:


The runner starts only its own disposable Testcontainers services and cleans up the fixture session, server, Redis and PostgreSQL on normal completion, setup/authentication errors and catchable SIGINT/SIGTERM. k6 receives SIGTERM on cancellation and is escalated after three seconds; the fixture server is given ten seconds before escalation. SIGKILL of the parent, host/container-runtime failure, or a runtime that cannot complete termination can still prevent synchronous cleanup. Do not run this command against a production database, endpoint or provider; the command accepts no target URL or externally supplied fixture identity.
