## Implementation and boundaries

- Production HTTP requests and initial realtime authentication verify an active Clerk session bound to the JWT's same user/session IDs. Production Socket.IO and Yjs factories also recheck it during existing passive/inbound audits. Positive lookups coalesce for at most5 seconds per process, with bounded2000-entry cache and1500ms provider deadline. JWT expiry remains independently enforced. Cache TTL uses monotonic time so correcting the wall clock backwards cannot retain authority. Provider outage/configuration failures deny; there is no auth bypass flag. Remote propagation, API limits and latency must be measured with the actual provider; no zero-delay revocation guarantee.
- New account settings at `/settings` list at most100 own active provider sessions, distinguish current session, require confirmation for revocation and expose provider failures honestly. No token, IP address, device fingerprint or password is returned. Another user's session cannot be revoked. Native Clerk sign-out remains the browser sign-out mechanism; cookie clearing remains separate from provider revocation. The list explicitly identifies truncation rather than claiming a complete inventory.
- AuthProvider withholds workspace children until verified local identity sync succeeds, exposes explicit uncached-token recovery and reports failed sign-out. A delayed sign-out failure after switching accounts cannot restore the former account's token getter. Clerk identity IDs remain provider IDs in the existing frontend context; workspace role decisions still use the existing local `/auth/me` mapping.
- Workspace settings retain members/invitations and add an explicitly opened lifecycle section, metadata editing, exact-name-confirmed ownership transfer and export-request recording. Transfer holds the existing current-owner tenant transaction, validates an active same-tenant target, promotes that member and demotes the caller to EDITOR atomically, then evicts stale transports. It cannot target self, foreign or inactive members. Existing role APIs and last-owner protections remain.
- `WorkspaceExportRequest` is an additive table with forced tenant RLS and one request per workspace/requester. Only current owners can create/read review metadata; repeated requests reuse the record. Status is **REVIEW_REQUIRED**, not queued/completed. No file, snapshot, email, provider call or export worker is created. Owner/operator review of scope, confidentiality, retention and delivery is still required.
- The account deletion plan reads only the caller's owned-workspace metadata and reports sole active ownership. It deletes nothing. No account deletion endpoint, automated erasure, legal hold policy, cross-provider cleanup or backup purge was invented. Workspace settings explain retained recovery copies and deletion prerequisites without a destructive button. Existing deletion API contracts were not silently replaced.
- Production-authenticated lifecycle mutations require a bearer header as well as authenticated identity; cookie-only POSTs cannot select a mutation. New routes use compatible `/api/v2` paths; current v1/legacy and WebSocket names remain. OpenAPI includes all new operations.
