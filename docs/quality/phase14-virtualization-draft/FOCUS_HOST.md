# Virtuoso focus-host experiment — not ready for integration

The current Kanban uses focusable per-card task buttons and owner/editor Move comboboxes, a Radix task drawer that restores focus to its original trigger when connected, and native HTML drag handlers. The TanStack draft pins focused, dragged and selected task IDs. This experiment does not replace any of those behaviors.

## Pattern and fixture

A standalone 1,000-task Virtuoso fixture uses the documented scroller as a persistent `role="grid"` focus host. Arrow keys change an active task ID and call `scrollToIndex`; visible rows expose `aria-rowindex`, a gridcell name and a visible outline. The host uses `aria-activedescendant` only while the active row exists in the DOM. On an offscreen row it clears that attribute and presents a polite status message; an arrow key scrolls to the next task. Enter opens a simplified fixture dialog and Escape returns focus to the host. A separate fixture action group exposes an Open button and a native Move select for the active task.

This is a grid experiment because the [WAI-ARIA listbox pattern](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/) does not support interactive controls inside its options. [WAI-ARIA](https://www.w3.org/TR/wai-aria/#aria-activedescendant) requires an active-descendant reference to identify an owned element, so the experiment does not reference an unmounted row. Clearing it is an accessibility tradeoff, not a verified substitute for the currently focused card.

`virtuoso-poc/focus-host.tsx`, `focus-host-index.html`, `focus-host-check.cjs` and `focus-host-results.jsonl` retain the fixture and observations. Focused ESLint and strict TypeScript passed with React Virtuoso temporarily linked from a separate directory. An initial typecheck failed on a ref/event type mismatch; those fixture types were corrected. No lint rules were suppressed.

## Results and limitations

Two local Chrome fixture runs passed the scripted checks at 1440px and 390px. Each rendered 10 task rows initially, after scrolling to the end, and after resizing. The host retained DOM focus when the active row unmounted; its active-descendant attribute was absent and the status text identified the offscreen active task. An arrow key returned to a rendered task. Enter opened the simplified dialog; Escape restored host focus. Tab reached Open, the Move select and a following control; Shift+Tab returned to Move. Selecting a fixture value did not call an API or move a real task. Automated axe on the final standalone fixture's initial state reported zero violations and zero incomplete results at both widths. Earlier fixture versions reported `aria-required-children` for a nested focusable scroller and `scrollable-region-focusable` after removing its tab stop; using the scroller itself as host eliminated those automated findings.

The checks do **not** establish screen-reader announcement behavior, full grid keyboard conformance, real Radix combobox/drawer behavior, native drag, authorization, persistence, reorder or focus restoration after a task moves or is removed. In particular, the separate active-task toolbar and arrow-key grid change the current per-card Tab/action model; this has not been shown equivalent to the existing board. No manual screen-reader test was performed. The existing TanStack prototype and all other uncommitted work remain intact, and no production integration or commit was made.

Kanban remains the clearest identified large-list target: workspace activity is capped at 20, inbox at 26 and search at 50. Decision receipts have a 200-item workspace limit, but a different surface should be chosen only after measuring its actual rendering cost and confirming its interaction and authorization requirements. A safe next step is to validate a complete rich-grid interaction model—including real per-task controls, offscreen announcements, drag overlay, focus restoration and assistive technology—before considering integration. Phase 14 remains open.
