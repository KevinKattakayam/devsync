## Core probe

A temporary minimal `@tanstack/virtual-core` adapter constructed `Virtualizer` in a React state initializer, supplied the scroll ref, called the core instance's `_didMount()` and `_willUpdate()` from layout effects, and read `getVirtualItems()` in render. Focused ESLint exited 1 with `react-hooks/refs`: passing the scroll ref through the initializer could read it during render. The installed official React adapter uses the underscore-prefixed lifecycle methods; their use in an application adapter, a concurrent-safe immutable snapshot and focused/dragged/open item retention were not established as a supported public React integration. A different external-store design might be possible; this probe does not prove impossibility. A production use of core also requires declaring it directly instead of relying on the current transitive installation. The temporary probe was removed.

## React Virtuoso probe

React Virtuoso 4.18.21 was installed in a temporary directory and exposed by a temporary `node_modules` symlink. A temporary Next route rendering a 1,000-item `<Virtuoso>` passed focused ESLint, repository strict TypeScript and `next build --webpack` (all exit 0). The route and symlink were removed, and the actual application build was rerun. Because this repository does not enable React Compiler, this establishes compatibility with its current lint/type/build configuration only; it does not establish behavior under an enabled compiler.

The [Virtuoso API](https://virtuoso.dev/react-virtuoso/api-reference/virtuoso/) documents measured dynamic rows, overscan, range callbacks and fixed top items. No supported mechanism for retaining arbitrary offscreen focused, dragged and open items was identified in that API review. Increasing overscan to span an arbitrary retained row may defeat the bounded-DOM goal. The [keyboard navigation example](https://virtuoso.dev/react-virtuoso/virtuoso/keyboard-navigation/) needs evaluation alongside Kanban's native drag, Radix move controls and drawer focus restoration. No production Virtuoso integration was completed, and no claim is made that a safe solution is impossible.

## Isolated interaction follow-up

The [Virtuoso proof of concept](virtuoso-poc/README.md) used 1,000 synthetic rows in local Chrome at 1440px and 390px. Dynamic long-row measurement and a simplified scroll-back drawer focus restoration worked; scrolling the focused row out of the rendered window moved focus to `BODY`. A native drag could drop after source unmount, but its fixture `dragend` callback did not fire and Escape left fixture drag state stale. An isolated dnd-kit `DragOverlay` preserved the overlay and handled pointer drop and Escape cancellation after source unmount, with 9 rows rendered at both widths. These are standalone fixtures, not tests of the board's real persistence, permission checks or screen-reader behavior. Focused fixture lint, strict types and one component test passed. No production replacement was applied because focused-row retention remains unresolved and switching the board to dnd-kit requires additional interaction and authorization verification.

## Kanban integration feasibility review

**No safe replacement is established.** This is a source and existing-evidence review; no production UI was modified and no new browser or screen-reader test was performed. The existing uncommitted prototype was preserved.

| Current interaction       | Existing path                                                                                                                                                                                       | Focus-host fixture and gap                                                                                                                                                                               |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Task selection and drawer | Card title button stores its DOM node in `taskTrigger`, sets the selected task and opens Radix Drawer; double-click also opens it.                                                                  | Host Enter opens a simplified dialog for an active index. It does not preserve direct Tab access to each title button or the real drawer.                                                                |
| Keyboard move             | Each writable card has a Radix `Select` named `Move <title>`; `moveTask` guards `canWrite`, `busy`, local IDs and same-column moves, then updates local boards and calls the existing task API.     | A separate native select changes a fixture value. Grid arrows/toolbar introduce a different focus model; Radix portal focus, cancellation, destination and authorization behavior are unproven.          |
| Native drag               | `handleDragStart` records the task and sets `text/plain`; column `onDragOver`/`onDrop` call `moveTask`.                                                                                             | Virtuoso can unmount the source. A separate dnd-kit overlay fixture handles pointer drop/cancel, but replacing native drag and preserving sensors, destination handling and permissions is not verified. |
| Drawer close and reorder  | Close focuses `taskTrigger` if connected, else the board heading. A move removes the card from one column and inserts it at the destination; a deleted or moved trigger may no longer be connected. | The fixture restores the persistent host after a simplified dialog. It does not resolve the moved task's new column/index, restore the actual card trigger, or verify deletion/revocation.               |

A persistent host can coexist with per-card controls only with an explicit composite-widget entry/exit contract: the host must not intercept keys while focus is inside a button or Radix portal, and it must restore the active task by stable ID after each DOM/data change. A grid may support interactive descendants with a carefully implemented focus mode, but the existing Tab sequence and offscreen focus semantics are not proven equivalent. A listbox is unsuitable for nested interactive controls ([WAI APG](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/)); an `aria-activedescendant` must refer to an owned element ([WAI-ARIA](https://www.w3.org/TR/wai-aria/#aria-activedescendant)). Clearing it when the row is absent and announcing text is not yet validated with assistive technology. Do not infer that a persistent host automatically protects a focused Radix trigger or a native drag source from unmounting.

Keep the existing board implementation available behind the flag, default it off until verified, and roll back by disabling the flag; no data migration or API change is required. Test both flag states and preserve existing authorization on the server. This is a proposed rollout plan, not an implemented flag. Do not claim Phase 14 complete until the original virtualization and accessibility acceptance checks pass.

## Isolated integration proof with real shared controls — focused pass

The standalone fixture in [`interaction-fixture`](interaction-fixture/RESULTS.md) uses React Virtuoso 4.18.21, 1,000 synthetic tasks, the repository's real shared Radix `Select`, and the real shared `DrawerContent`/Radix Dialog implementation. The task title button mirrors the inline Kanban button's task name, activation and trigger-ref behavior because the production card is not an extractable component. Production Kanban, API, CRDT state and drag handlers were not changed.

The grid host keeps DOM focus while arrow navigation updates a stable task ID; `aria-activedescendant` is emitted only for a mounted row. A focused title that scrolls out of the range is deliberately handed off to the persistent host, and the status announces the active item. Browser Tab/Shift+Tab checks crossed the title and real Radix Move control and exited/re-entered the rendered task window. The real drawer restored focus to its connected title trigger; after a fixture move, deletion or access revocation it used the persistent board heading fallback. The viewer fixture hid Move controls and disabled drawer mutations; simulated revocation closed the drawer and removed all task rows.

At both widths the 1,000-task fixture rendered 8 rows initially and at the end of the list, and 20 after all interactions/resize-related layout activity (all below the recorded 40-row bound). Initial-state axe reported 0 violations and 0 incomplete checks at 1440px and 390px. This is browser automation on synthetic data; no manual screen-reader test, live membership revocation, real board persistence, API authorization or drag/drop integration was performed.

The first regression run exposed two separate issues. The desktop test sent Enter before the Radix highlighted option was ready; the browser script now waits for the “Done” option to be focused and highlighted. The fixture's `rangeChanged` callback also confused a removed task (index `-1`) with an offscreen task and restored its ID. It now ignores IDs absent from the current list, while the move handler selects an adjacent remaining task and focuses the persistent host after Radix closes. These fixes are limited to the isolated fixture.

The corrected fixture passed twice at 1440px and 390px. It moved the last To do task to Done through the shared Radix keyboard control, retained host focus, announced “Task 999, task 999 of 999,” kept `aria-activedescendant` absent or valid, and preserved first-page order. Each viewport showed 8 initial/end rows and 20 after interactions; axe reported zero violations/incomplete checks before and after the move. Detailed counts and commands are in [fixture results](interaction-fixture/RESULTS.md).

The focused interaction proof is ready for a controlled, reversible Kanban integration proof; it does not certify the production board. The title button is mirrored because the board card is inline, and synthetic fixture state does not exercise the production move API, permission changes, server rejection/undo, native drag source, CRDT persistence, or assistive technology. Verify those against the actual board behind a feature flag before adopting the virtualizer. Phase 14 remains open.
