# Combined Virtuoso and dnd-kit fixture — isolated evidence

This is a synthetic 1,000-task proof, not production Kanban. It combines the prior focus host, shared Radix Move and Drawer controls with a dnd-kit pointer sensor and DragOverlay. Virtuoso 4.18.21 was installed under `/tmp/devsync-phase14-virtuoso-integration`; Vite aliases React and React DOM to the frontend's installed copies. No production manifest or dependency was changed. All results use local Chrome and fixture state, not a provider or backend API.

## Results

- `check.cjs`: exit 0 at 1440px and 390px. Each run rendered 8 initial and 8 scrolled task rows; the dragged source unmounted, the overlay persisted, a destination drop moved the fixture task, and Escape cleared the overlay and returned focus to the list host. See `drag-results.jsonl`.
- `scenarios.cjs`: exit 0 at both widths. Invalid drop created no move; a fixture move was observed in the optimistic state before a timed simulated rejection restored its column. Simulated external viewer, deletion and revocation events during drag cleared the overlay; deletion selected a remaining active ID and focused the heading, and revocation removed visible rows. See `scenario-results.jsonl`. Dnd-kit intercepted direct button clicks during active pointer drag, so the external changes are deliberately injected as fixture events. Initial click-based attempts failed; they do not demonstrate external updates.
- `controls-check.cjs`: exit 0 at both widths. The prior keyboard, Radix Move, focus-host, Drawer and viewer fixture assertions passed after scoping status selectors to the task announcement because dnd-kit adds its own live region. Eight rows were present at the start/end and 20 after the full interaction sequence. Automated axe found zero violations and zero incomplete checks in the initial and post-Move states. See `controls-results.jsonl`. An initial combined run found that the new drag handle altered Tab order; it is now pointer-only in the Tab sequence, while the existing Radix Move control remains keyboard accessible.
- Focused ESLint with the frontend configuration and `--max-warnings=0`: exit 0 for the three fixture TSX files. Invoked from the repository root, ESLint printed React-version and pages-directory detection messages because those paths are outside the frontend base. Strict TypeScript against this fixture's `tsconfig.json`: exit 0. Focused Vitest component test: exit 0, 1 test; Vite reported unresolved optional `esbuild`/devtools imports while loading its configuration. The first component attempt failed from a second React copy; inlining Virtuoso and using the frontend React alias corrected it.
- `cd frontend && npm run build -- --webpack`: exit 0 in the permitted subprocess context. The isolated fixture is outside the production build.

## Reproduction and limits

Install `react-virtuoso@4.18.21` into `/tmp/devsync-phase14-virtuoso-integration` without modifying frontend manifests. Run Vite with this directory as root and `vite.config.mjs`, then run the three `.cjs` checks against localhost port 3419. `vitest.config.mts` and `tsconfig.json` use local absolute paths and the temporary installation; adapt them for another machine. The fixture uses `DndContext` remounting after simulated external access changes, which can reset list state. Its timed rollback restores the fixture task's column only; it is not a real API rejection, concurrency test, tenant authorization or proof that acknowledged state is durable. Viewer/revocation events are simulated. Real server permission changes, races, optimistic rollback/undo, native board contracts, screen-reader review, focus and scroll behavior after remount, and the production browser suite remain unverified. The pointer handle is excluded from Tab order; keyboard moves use the existing Radix control and still need manual assistive-technology review. This proof is not authorization to integrate, and Phase 14 remains incomplete.
