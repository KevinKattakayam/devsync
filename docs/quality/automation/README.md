# Phase 10 automation — local implementation and outstanding acceptance

The feature is disabled by default via `FEATURE_AUTOMATION` and `NEXT_PUBLIC_FEATURE_AUTOMATION`. Workspace owners can create a rule disabled, preview current authorized sources, enable it and separately approve each pending execution. Nonowners cannot create, approve or view execution history; GitHub configurations and evidence remain owner-only. Task review/blocker events are explicit writer assertions rather than automatically inferred from Kanban columns. A local notification/escalation creates a workspace activity transactionally; it does not send mail or make external writes. Deleted task activity derivatives are filtered on read.

Signed webhook observations can prepare a PR report from existing recorded evidence after approval. They are not independent proof of live provider access. An individual successful check does not establish aggregate CI or deployment. The CI linked-status action returns `ci_verification_unavailable` and performs no task mutation: a trusted verification adapter/policy and the unfinished linked-work graph are still needed. The automation path neither calls AI nor performs external writes. Existing unrelated PR-summary behavior is unchanged.

Event hashes are workspace/actor scoped, with durable deduplication and serialized debounce. Pending work is rescanned from Postgres; BullMQ gets an execution UUID and encrypted tenant locator only. Leases, three attempts, timeouts, source/membership rechecks, generic error codes and transactional local activities protect retries. Redis outage and ACL behavior use a dedicated bounded producer. Audit exposes the latest 100 executions, not pagination. Disabled rules do not execute. No automated actions emit new automation events, bounding feedback loops.

## Migration and rollback

The additive migrations `202611090001_automation_rules` and `202611090002_automation_executions` use forced tenant RLS and composite tenant relationships. Isolated browser/database tests applied the chain. Before any production rollout, independently review grants, backups and restore, identity retention and the migration plan. Actor references restrict deletion and require account lifecycle policy review. Disable both feature flags and stop/drain automation workers to roll back behavior; retain tables and audit data pending an approved retention/migration plan. No destructive down migration or production migration has been run.

For live acceptance, create a separate approved disposable GitHub test repository and App, configure narrowly scoped installation and webhook credentials privately, then agree separately on any external write or redelivery. No provider credentials should be logged. Implement and review the missing trusted CI verification and work-graph integration before enabling linked-status updates; credentials alone do not complete that work.
